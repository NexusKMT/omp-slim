# Environment Variables (Current Runtime Reference)

This reference is derived from current code paths in:

- `packages/coding-agent/src/**`
- `packages/ai/src/**` (provider/auth resolution used by coding-agent)
- `packages/utils/src/**` and `packages/tui/src/**` where those vars directly affect coding-agent runtime

It documents only active behavior.

## Resolution model and precedence

Most runtime lookups use `$env` from `@oh-my-pi/pi-utils` (`packages/utils/src/env.ts`).

`$env` loading order:

1. Existing process environment (`Bun.env`)
2. Project `.env` from the launch working directory for keys whose current value is empty/unset
3. Active agent `.env` (normally `~/.omp/agent/.env`) for keys whose current value is empty/unset
4. Active config-root `.env` (normally `~/.omp/.env`) for keys whose current value is empty/unset
5. Home `.env` (`~/.env`) for keys whose current value is empty/unset

The agent/root locations respect profiles, `PI_CONFIG_DIR`, and—only for the default profile—`PI_CODING_AGENT_DIR`. Whole dotenv files are parsed with Bun's `node:util.parseEnv`, including quoted multiline values, escaped newlines, and inline comments. Names must be shell identifiers (`[A-Za-z_][A-Za-z0-9_]*`); unsafe names/values are discarded. Variable references remain literal in this parser; only Bun's launch-directory dotenv autoload performs variable expansion before this module runs. Child-shell filtering uses the same parser to identify project dotenv values across `.env`, `.env.<NODE_ENV>` (default `development`), `.env.local`, and `.env.<NODE_ENV>.local`. It removes project-dotenv credentials from shell subprocesses while preserving launcher-owned variables; Linux's original exec environment provides the authoritative launch snapshot, with best-effort value matching elsewhere.

Additional rule inside each `.env` file: every `OMP_*` key is mirrored to its `PI_*` alias, and that mirrored value replaces a same-file `PI_*` value. This mirroring applies to parsed dotenv files, not arbitrary variables inherited from the parent process.

Variables declared on a setting definition (see [settings precedence](./settings.md#precedence)) outrank every settings file but yield to a runtime override such as a CLI flag. They are parsed by the setting's type unless noted otherwise. Boolean ones (`PI_PY`, `PI_JS`, `PI_INTENT_TRACING`, `PI_AUTO_QA`, `HINDSIGHT_AUTO_RECALL`, …) follow `parseFlag`: an empty value is ignored, so the setting applies; `1`, `y`, `true`, `yes`, and `on` (all-lowercase or all-uppercase) mean true; any other non-empty value means false.

## 1) Model endpoint authentication

Endpoints and models are explicitly configured in `models.yml`; see
[Models](./models.md) and [Providers](./providers.md). The namespace-derived key
fallback is `<PROVIDER>_API_KEY`: uppercase the configured provider name and
replace non-alphanumeric characters with `_`. For provider `local-chat`, the
variable is `LOCAL_CHAT_API_KEY`. This fallback reads the process environment.

An explicit `apiKey` or header value in `models.yml` can reference an exact
variable name using the configuration value resolver. The `.env` loading rules
above apply to that resolver. A provider with `auth: none` requires no key.
There are no built-in supplier credential aliases, OAuth tokens, broker/gateway
variables, or model-discovery endpoint variables.

## 2) Model transport configuration

Chat Completions requests resolve outbound proxies in this order, after local
network and `NO_PROXY` exclusions:

1. `PI_PROXY_<PROVIDER>`, using the normalized configured namespace.
2. `PI_PROXY`.
3. `HTTPS_PROXY` / `https_proxy` for HTTPS, or `HTTP_PROXY` / `http_proxy` for HTTP.
4. `ALL_PROXY` / `all_proxy`.

Provider proxy lookups are cached for the process lifetime. Loopback,
link-local, private network and cloud metadata targets bypass the proxy.
`PI_PROXY` also wraps process-wide fetches at CLI startup.

`NODE_EXTRA_CA_CERTS` adds a custom CA bundle for Bun fetches. It accepts a file
path or inline PEM; the standard root certificates remain included unless the
caller has explicitly supplied its own CA list. A missing bundle is a
configuration error.

`PI_NO_STRICT` bypasses strict function-schema adaptation. Endpoint capabilities
and wire fields are otherwise declared in `models.yml`, including
`compat.maxTokensField`, `supportsUsageInStreaming`, `supportsDeveloperRole`,
`supportsStrictMode`, and `supportsStore`.

## 3) Web search and fetch

Search backends are separate from model inference. Current integrations use
public search pages, SearXNG, Exa, Firecrawl and Parallel; no supplier model
request is used as a search fallback.

| Variable | Use |
| --- | --- |
| `EXA_API_KEY` | Exa search authentication. |
| `FIRECRAWL_API_KEY` | Firecrawl search and fetch reader authentication. |
| `FIRECRAWL_BASE_URL`, `FIRECRAWL_API_URL` | Firecrawl endpoint override; the first takes precedence. |
| `PARALLEL_API_KEY` | Parallel search and fetch authentication. |
| `SEARXNG_ENDPOINT`, `SEARXNG_TOKEN` | SearXNG endpoint and optional bearer token, used when the corresponding setting is unset or blank. |
| `SEARXNG_BASIC_USERNAME`, `SEARXNG_BASIC_PASSWORD` | SearXNG HTTP Basic credentials, used when the corresponding setting is unset or null. |
| `GITHUB_TOKEN`, `GH_TOKEN` | GitHub scraper API authentication; `GITHUB_TOKEN` takes precedence. |

Public search does not require model credentials. SearXNG settings under
`searxng.*` take precedence over their environment fallbacks.

## 4) Python tooling and kernel runtime

| Variable               | Default / behavior                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------- |
| `PI_PY`                | Boolean flag override for Python; unset or empty defers to `eval.py` (default enabled)              |
| `PI_JS`                | Boolean flag override for JavaScript; unset or empty defers to `eval.js` (default enabled)          |
| `PI_PYTHON_SKIP_CHECK` | Truthy flag skips Python interpreter availability checks (subprocess runner still starts on demand) |
| `PI_PYTHON_IPC_TRACE`  | Truthy flag logs NDJSON frames exchanged with the Python runner subprocess                          |

`PI_BASH_NO_CI`, `PI_BASH_NO_LOGIN`, and `PI_SHELL_PREFIX` use their `CLAUDE_*` aliases when the canonical variable is unset or empty. These controls use non-empty string checks, not boolean parsing: even `0` or `false` activates the corresponding no-CI/no-login control.

### Set by the `bash` tool

Every command the agent runs through the `bash` tool (foreground, background, PTY, ACP client terminal, and `name`-launched services) receives the current session identity and the id of the tool call running it:

| Variable          | Value                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------ |
| `PI_SESSION_ID`   | Current session ID                                                                         |
| `PI_SESSION_FILE` | Absolute path to the current session JSONL file; empty when not persisted (`--no-session`) |
| `PI_TOOL_CALL_ID` | ID of the `bash` tool call running the command                                             |

Values are read when each tool call starts, so the next call follows `/fork`, `/new`, and `/resume`, and a call already under way keeps the session it started in. They are always set, so an empty value replaces a stale one inherited from a parent omp process. User `!` commands do not receive them.

`PI_TOOL_CALL_ID` matches the `toolCall` entry in `PI_SESSION_FILE` when the agent called `bash` itself (a subagent's call is in the subagent's own transcript). A `bash` call made from an `eval` cell through the tool bridge gets the bridge's generated id (`js-bash-…`), which no transcript entry carries; the transcript records the `eval` call instead.

```bash
echo "$PI_SESSION_ID"
```

| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `PI_LINK_SCHEME` | Custom file-link scheme, for example `ompfile`, without `:` or `://`. Matched case-insensitively against `^[a-z][a-z0-9+.-]*$` and emitted lowercase. An invalid value logs a warning and keeps ordinary file/VS Code targets.             |
| `PI_LINK_HOST`   | Remote machine name used with `PI_LINK_SCHEME`, optionally with `:port`; defaults to `os.hostname()`. Letters, digits, `.`, `_`, and `-` only; an invalid value logs a warning and keeps ordinary targets. Has no effect without a scheme. |

The interactive TUI reads these variables once at startup. Both OSC 8 links and native TSP file links use the custom scheme, which takes precedence over VS Code targets. SDK hosts can call `applyFileLinkSetting` with an explicit configuration. Native image context-menu open actions keep local `file://` URLs because the action runs locally.

For example, start a remote session with `PI_LINK_SCHEME=ompfile PI_LINK_HOST=beelink omp`. A file link to `/work/a b.ts` at line 42, column 7 targets `ompfile://beelink/work/a%20b.ts?line=42&col=7`. The optional `line` and `col` query parameters preserve the supplied position; absent values are omitted. Plain `file:` links never carry these parameters.

The desktop protocol handler must route the host to the remote machine, percent-decode the pathname, and read the optional position parameters. Windows drive paths use `/C:/...`. UNC paths retain the file server in a double-slash pathname, for example `ompfile://beelink//nas/share/a.ts`. Malformed filesystem paths render without a link. File links the model writes in Markdown keep their own query or fragment (for example `#L10`), so handlers must ignore parameters they do not recognize. The handler itself is registered separately on the desktop.

## Security-sensitive variables

Treat these as secrets; do not log or commit them:

- API keys, bearer credentials, and MCP OAuth credentials
- Cloud credentials (`AWS_*`, `GOOGLE_APPLICATION_CREDENTIALS` path may expose service-account material)
- Search authentication variables (`EXA_API_KEY`, `FIRECRAWL_API_KEY`, `PARALLEL_API_KEY`, SearXNG credentials)
- Custom TLS trust material (`NODE_EXTRA_CA_CERTS` when it points to private CA bundles)
- OTLP exporter headers (`OTEL_EXPORTER_OTLP_HEADERS` and the per-signal `..._{TRACES,LOGS,METRICS}_HEADERS` variants) — they carry ingest bearer tokens/project keys

Python runtime also explicitly strips many common key vars before spawning kernel subprocesses (`packages/coding-agent/src/eval/py/runtime.ts`).
